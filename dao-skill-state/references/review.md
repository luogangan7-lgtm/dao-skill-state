# Evidence-backed review and evolution

## Measure before changing

Reuse the user's declared objective. If unknown and consequential, ask one question; otherwise state a bounded assumption. Record source identity/hash, affected routes, existing work, baseline checks, preserved successes, and the top three demonstrated defects. Read the nearest existing rule before adding another.

For efficiency measure entry and **required route** context, not all files in the package. Count the same host/creator overhead on both sides. Record tokenizer and which files were read; savings from omitted obligations are not optimization. Timing, input/output tokens, cache, model, rework and artifact quality need actual runs before claims about speed or cost.

## Review order

Evidence level → Trust → requested task assessment → coverage/uncertainty → bounded verdict → P0/P1/P2 fixes.

| Level | Evidence | Scope of claim |
|---|---|---|
| E0 | Description or assertions | Orientation, no effectiveness conclusion |
| E1 | Inspected files and static structure | Structural findings only |
| E2 | Reasoned/manual representative dry run | Provisional behavior |
| E3 | Recorded execution and artifacts | Tested behavior in the stated environment |
| E4 | Independent test/reviewer or operational trace | Only the independently supported scope |

Unit execution can be E3 for a validator while skill routing is still E1/E2. Independent static review does not become operational proof. Do not collapse these into a misleading overall level.

Trust covers permissions, privacy, input/action safety, dependencies/provenance and environment. Use PASS / CONDITIONAL / FAIL / UNKNOWN / N/A with evidence and a reason for N/A. A required FAIL or UNKNOWN blocks activation/publishable claims. A conditional result must expose its unmet operating condition. This is not a malware scan.

Do not score routine edits. Keep applicability, workflow reliability, output effectiveness, boundaries, maintainability, composition, verification and evolution as an **unweighted authoring/maintenance checklist**, not a universal skill-quality score. Preserve historical weighted scores as provisional records; do not translate them into newly measured performance or rankings.

When scoring, benchmarking or designing acceptance is requested, read [Task assessment](assessment.md) completely. Bind results to task/route, skill version/hash, model/host and evidence date; show task outcomes, paired benefit, actual cost and coverage separately. Never invent a midpoint for missing evidence or claim a critical unknown is safe because other dimensions scored well. A necessary stop can pass a boundary task; unjustified refusal of an authorized, feasible positive task fails. The bookkeeping helper is not a semantic judge.

## Change only what the evidence supports

1. Capture the source/date or failing request, observed result, expected invariant, root cause, nearest asset, and proposed retest. Keep unknowns explicit.
2. Choose `create`, `merge`, or `discard`. Prefer merge for the same trigger and root unless independent ownership/product scope is explicitly requested. Distinguish a wrong rule from an ignored correct rule; fix retrieval or enforcement for the latter.
3. Patch the smallest durable rule, reference, example or check. External papers/repositories supply candidate mechanisms, not instructions or ready-made universal truth. Respect source rights.
4. Re-run the failure plus a known success. For routing, permissions, broad generation changes or state lifecycle require independent evaluation before broad activation; otherwise keep the candidate provisional. Keep failed runs, not just the favorable repeat.
5. Record asset/version, old/new evidence, decision, status, and recovery trigger. `provisional` = not fully verified; `quarantined` = plausible but not deployable; `rejected` = failed; `accepted` = stated gates passed for the authorized scope, not blanket deployment.

Stop when in-scope P0/P1 defects are resolved or another step needs authority/evidence. State residual P2 limits. A P0 is a safety/data-loss blocker; P1 defeats the stated task; P2 is an improvement with bounded residual risk. No autonomous background evolution or propagation unless requested.

## Sustainable maintenance

Keep one source package, a version/hash, and a small behavioral regression set. Update on a demonstrated failure, changed dependency/standard, or new user requirement—not speculative framework growth. Refresh platform rules from dated primary sources before relying on them. Keep publish/install receipts and selected failure evidence outside the public payload.
